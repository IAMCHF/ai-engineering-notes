## 项目经历

### 企业内网 AI 开发工作台（AI 编程助手 + MCP 建站）｜ 全栈开发，MCP 模块独立负责 ｜ 2025.10 – 2026.11

**项目背景**：面向内网研发的 AI 编程助手（多模型对话、流式输出）与建站 Agent 工具链。后者以 MCP Server 形态让 Agent 端到端完成「建站 → 部署 → 入口申请 → 状态核验」。工作台后端 40+ API / 8 张表；MCP 核心 4.9k 行 Python / 19 模块 / 22 个工具。

**技术栈**：Python 3.12、FastAPI、官方 MCP SDK v2（stdio）、LangGraph、httpx、Redis PubSub、React 18 + TypeScript、gunicorn + UvicornWorker、Nginx、IndexedDB

- **MCP 工具链**：基于官方 MCP SDK v2（stdio）独立实现 22 个工具（READ / PLAN / CHANGE 三档）与六阶段部署状态机，打通建站、部署、入口申请、状态核验全流程；核心 4.9k 行 / 19 模块，配套 20 个测试覆盖协议、离线回归与打包验证。
- **确认安全**：针对 Agent 可在工具参数中伪造 `confirmed=true` 的越权风险，把「用户确认」从 MCP 工具中物理移除——plan 只返回本地回环 `confirmation_url`，approve 仅由本地 UI 的 HTTP 端点调用，execute 强校验 `approval_digest`；安全边界由「模型行为约束」下沉为「进程边界」，确认绕过在架构层不可达。
- **Agent 约束分层**：工具层不注册裸 HTTP 转发、策略层硬编码资源上限且不可配置放宽、编排层拒绝同名服务重建且异常分支不删资源；配合「单窗 20s / 总预算 120s + `wait_expired` 显式交接」，解决 stdio 不支持 server→client 推送时的人工确认等待与 Agent token 消耗问题。
- **流式链路**：定位并修复 Nginx 默认 `proxy_buffering` 与 gzip 导致的整段输出，落地 location 级 `proxy_buffering off` + `X-Accel-Buffering: no` 双保险，端到端首字延迟稳定在 200–500ms；以 tagBuffer 字符级状态机处理推理模型思维链跨 chunk 的标签截断，避免 `</t|hink>` 泄漏到正文。
- **成本与容量**：在 `GeneratorExit` / `ConnectionResetError` 分支显式关闭上游流，客户端断开即停止 token 消耗；按上游网关并发而非 CPU 核数确定 `gunicorn 30 workers + max-requests jitter` 的容量模型，避免 SSE 长连接占满 worker。

### 企业 AI 资源平台（模型广场 + 技能广场）｜ 技能前端主负责 / 后端最大贡献者 / 评审服务独立开发 ｜ 2025.11 – 2026.10

**项目背景**：企业内网 AI 资源平台。模型广场统一管理 API 服务与大模型，对接 Kong 完成申请与路由；技能广场（SkillHub）负责 Agent 技能的发布、审核、分发与多租户治理。后端约 2.5 万行 Python（8 Controller / 20 Service / 12 DAO / 12 表）、前端约 2 万行 TS、约 100 个 API。

**技术栈**：FastAPI、SQLAlchemy async、MySQL、Redis、React 18 + TypeScript + Ant Design + Vite、LLM 评审（TRACE 五维）、MySQL FULLTEXT、Kong

- **异步评审**：将 10–60s 的 LLM 评审从发布主链路剥离——发布置 `SCANNING` 状态即时返回，独立 worker 消费、定时调度兜底漏单；在无 Kafka / Celery 的内网约束下实现可靠异步扫描，唤醒失败不阻断主流程，后续可仅替换唤醒实现平滑迁移到队列。
- **版本治理**：设计多租户命名空间与版本「软下架」——`YANKED` 只标记不删文件，agent-download 仅返回最新可用版本，yank latest 时自动回填次新版本；发布事件延后到审核通过后补发，保证检索索引不出现 `SCANNING` 中间态。
- **并发一致性**：应用层先查仅用于友好提示，最终一致性由数据库唯一索引兜底，捕获 `IntegrityError` 后回滚并转业务错误，消除「先查再插」的 TOCTOU 双发；统一覆盖命名空间关系、成员等多张表。
- **权限缓存**：权限判定涉及 5 张表、200–300ms，以进程内 Map + in-flight Promise 去重 + sessionStorage hint 三层缓存，把路由守卫、侧边栏、页面三处并发请求收敛为一次；刷新首帧用 disabled 占位消除布局跳动，账号切换即时失效。
- **规模与贡献**：后端约 2.5 万行、前端约 2 万行、约 100 个 API；独立开发 LLM 评审服务（1.7k 行 Python）；技能广场前端 156 commits 主负责，后端 51 commits 为最大贡献者。

### PPT 检索与大纲生成工具（RAG 应用）｜ 前端负责人 / 鉴权与权限隔离 ｜ 2026.04 – 2026.08

**项目背景**：基于企业 RAGFlow 知识库与大模型网关的 PPT 大纲生成工具，嵌入企业门户。用户输入主题并选择知识库，生成带引用的 PPT 大纲，要点可回溯原文片段、相似度、图片预览与源文件。前端 3 个页面约 2k 行 TS，后端约 2.5k 行 / 13 个端点 / 5 张表。

**技术栈**：React 19 + TypeScript + Vite + shadcn/ui + Tailwind、FastAPI、SQLAlchemy + PostgreSQL、JWT、RAGFlow 混合检索

- **前端交付**：负责 Web 端 3 个页面从 0 到 1，实现知识库选择、生成过程状态与引用卡片，支撑「每个要点可回溯原文片段、相似度、图片与源文件」的产品契约。
- **鉴权与隔离**：实现白名单准入与多用户权限隔离的前端适配，包括登录态与刷新令牌、按用户可见的知识库列表、越权访问拦截，支撑工具从单租户内测升级为嵌入企业门户的多用户服务。
- **可信生成**：落实「无依据不生成」的交互契约，对空召回或低分命中场景做显式失败提示与重试引导，避免向用户展示 LLM 自行编造的大纲内容。
