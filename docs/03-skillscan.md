# 案例 B · SkillScan TRACE（个人项目，可公开）

> 位置 `C:\projects\skillscan`。业余时间在外网完成，后拉到内网使用，未上生产、内网改动不大。
> **性质：个人项目，不受 AGENTS.md 第 4 条约束**，可直接开源（公开前须处理 §6）。
> 规模：16 个 Python 文件 / 2,227 行 + 718 行 Jinja2 模板；6 个依赖；26 次提交。
> 逐项待办见 [03-skillscan-tasks.md](03-skillscan-tasks.md)。

---

## 1. 它是什么

技能（skill zip）上线前的**静态安全与质量审核服务**：上传 zip → 纯静态提取文本（**绝不执行**）→ 格式检测 → 分类 → LLM 按 TRACE 五维 20 项打分 → HTML 报告。

**为什么值钱**：它不是"调 API 的 demo"——它有**判定权**（通过 / 有条件 / 淘汰），并且对"审不出来"有明确策略。判定、降级、可复现，这三样是 LLM 应用从 demo 走向生产才会遇到的。

## 2. 做对的 5 点（别改）

1. **fail-closed**：LLM 不可用时判"淘汰"，理由写明"审核未完成，请重试或转人工"；
2. **最便宜的检查前置**：格式检测在 LLM 之前，不通过直接返回，省一次大模型调用；
3. **静态分析、不执行代码**：真实的安全边界；
4. **不伪造通过状态**：`security_labs` 如实反映每步结果；
5. **克制**：2,227 行、6 个依赖，无框架污染。

## 4. 技能检测可以省的时间

现状：Step 2 **先调 LLM 分类，失败才降级关键词**。但分类只用于报告分组，**不参与 verdict**——为纯展示字段多付一次往返（2–4s + token + 一个失败点），不划算。

| 方案 | 做法 | 省下 | 代价 |
|---|---|---|---|
| **A 直砍（推荐）** | 只走关键词，删 `SYSTEM_PROMPT_CLASSIFY` | 一次完整 LLM 往返 | 边界技能准确率略降（不影响判定） |
| B 懒调用 | 关键词置信度够就用，低置信度才补调 | 多数样本省一次 | 多一条分支 |

附带好处（比省时间更重要）：**分类结果变可复现**，不再受模型波动影响。

## 5. P1 才是真正的机会

一个用分数决定"放行还是淘汰"的系统，结论不稳定就不能用。补法：

**10–15 个固定样本 × 3 次重复 × 2 个模型** → 各维度标准差、verdict 一致率、单次成本、P50/P95。

能得出"verdict 一致率 92%，T 维度方差 ±0.8，temperature 从 0.3 降到 0 后收敛到 ±0.3"这样的结论，**一句话就顶三个普通项目**——因为它证明你会做评测，而不只是会写功能。

## 6. 公开前三项确认

1. **TRACE 体系能否公开引用**——README 写的是"某平台首发标准"。若属平台/公司资产，改用自己的五维体系（结构可同、命名与定义要换）。
2. **代码里有无公司资产**——内网版是否加过内部接口、账号、地址、平台字段。
3. **git 历史清理**——必须新建仓库，不要用 `filter-branch` 修老历史。
