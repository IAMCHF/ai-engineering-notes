# 案例 B · SkillScan TRACE（个人项目，可公开）

> 位置：`C:\projects\skillscan`。业余时间在外网完成，后拉到内网使用，未上生产，内网改动不大。
> **性质：个人项目，不受 [AGENTS.md](../AGENTS.md) 第 4 条约束**，可直接开源（但公开前须处理 §6 的三项）。
> 规模：16 个 Python 文件 / 2,227 行 + 718 行 Jinja2 模板；6 个依赖；26 次提交。

---

## 1. 它是什么

技能（skill zip 包）上线前的**静态安全与质量审核服务**：上传 zip → 纯静态提取文本（**绝不执行**）→ 格式检测 → 分类 → LLM 按 TRACE 五维 20 项打分 → 输出 HTML 审核报告。

**为什么它值钱**：它不是一个"调 API 的 demo"，它有**判定权**——放行 / 有条件通过 / 淘汰，而且对"审不出来"这种情况有明确处理策略。这三样是 LLM 应用从 demo 走向生产才会遇到的东西。

## 2. 设计上做对了什么（别改）

1. **fail-closed**：LLM 不可用时结论判"淘汰"，理由写明"审核未完成，请重试或转人工"。安全产品的正确姿态——宁可误杀。
2. **最便宜的检查放最前**：格式检测在调 LLM 之前，不通过直接返回，省掉一次大模型调用。这是成本意识。
3. **静态分析、不执行代码**：真实的安全边界，不是话术。
4. **不伪造通过状态**：`security_labs` 如实反映每一步执行结果。
5. **克制**：2,227 行、6 个依赖，没有框架污染。

> 这五点在面试里可以直接讲，是你区别于"套模板"的地方。

### P1 · 可复现性（最致命，也最值钱）

**同一份技能扫两次，TRACE 分数可能差 0.5–1.5 分。** 一个审核系统如果结论不稳定，就无法用于放行决策——这是当前最大的方法论缺陷，也是最好的补强机会。

修法（同时产出简历数字）：

- 固定 **10–15 个样本**（安全/可疑/恶意各若干）；
- 每样本跑 **3 次**，用 **2 个模型**（主用 + 备用）；
- 指标：各维度分数的**标准差**、`verdict` **一致率**、单次成本、P50/P95 延迟；
- 结论落到一句可量化的判断：例如"verdict 一致率 92%，T 维度方差最大（±0.8），需把 temperature 从 0.3 降到 0"。

### P2 · 工程化（最容易补，也最容易讲）

| # | 缺失 | 后果 | 修法 |
|---|---|---|---|
| 5 | 无重试 | 超时直接判淘汰，误杀率高 | 仅对超时/5xx 做一次指数退避重试 |

| 10 | 无 CI | 回归全靠手动 | GitHub Actions：安装依赖 + 跑单测 |

## 4. 关于"技能检测那块可以省时间"——你说对了，而且省得比你想的多

**现状**：Step 2 先调 LLM 做分类，失败才降级关键词。

**问题**：分类结果只用于报告里的分组展示，**不参与 verdict 判定**。为一次纯展示的字段多付一次 LLM 往返（+2–4 秒、一次 token、一个失败点），不划算。

**两个方案**：

| 方案 | 做法 | 省下 | 代价 |
|---|---|---|---|
| A 直接砍（推荐） | 分类只走关键词，删掉 `SYSTEM_PROMPT_CLASSIFY` 与那次调用 | **一次 LLM 往返**（2–4s + token） | 边界技能准确率略降——但分类不参与判定，可接受 |
| B 懒调用 | 关键词置信度 ≥ 阈值直接用；**只有低置信度才补一次 LLM** | 大多数样本省一次调用 | 保留一条分支，代码略多 |

顺带的好处（比省时间更重要）：**分类结果变得可复现**，不再受 LLM 波动影响。

改造量：方案 A 约半天；方案 B 约一天。
